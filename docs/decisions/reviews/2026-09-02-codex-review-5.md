# Codex adversarial review 5: the script VM commit 512bf16 (2026-09-02)

Disposition in `2026-09-02-codex-review-5-disposition.md`.

Commit `512bf16` is not mergeable. The clean-room violation is release-blocking, and the replay/sequence models need architectural changes rather than isolated patches. References below use line numbers from the committed tree, not the dirty working copy.

1. **Critical — the clean-room sweep is still incomplete.** The repository policy forbids original text strings ([AGENTS.md:17](C:/Users/przem/source/repos/opensherwood/AGENTS.md:17), [legal.md:20](C:/Users/przem/source/repos/opensherwood/docs/legal.md:20)), but the tree still transcribes an ordered seven-string slice from `Level.res` ([rhm.md:366](C:/Users/przem/source/repos/opensherwood/docs/formats/rhm.md:366)), the exact HUD format string ([ui_assets.rs:61](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-app/src/ui_assets.rs:61)), named antagonist data ([profile.md:93](C:/Users/przem/source/repos/opensherwood/docs/formats/profile.md:93)), and extensive asset-derived name/action catalogs ([sprite-animations.md:73](C:/Users/przem/source/repos/opensherwood/docs/formats/sprite-animations.md:73)). Exact proprietary values also remain in data tests ([gamedata.rs:807](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-formats/tests/gamedata.rs:807), [test_mission.py:103](C:/Users/przem/source/repos/opensherwood/harness/tests/data/test_mission.py:103)). This directly contradicts review-4 disposition row 1. The asset checker passes only because it explicitly does not detect copied text.  
   **Fix:** retain indices, counts, relationships, hashes and role descriptions; derive required runtime identifiers from player data; replace exact-value fixtures with relational assertions or synthetic names; perform another human text sweep outside `docs/decisions/reviews/` and disposition the already-pushed history.

2. **High — mission replays cannot reproduce their initial VM state.** Mission reset runs `PostInitialize` and opens the first script page ([engine.rs:967](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-app/src/engine.rs:967)). Recording is refused until the screen is `World`, so it begins only after the pages have mutated the VM at tick 0 ([engine.rs:1291](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-app/src/engine.rs:1291)). Playback resets to the pre-dismissal state, then bypasses screen handling via `step_recorded` ([engine.rs:1403](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-app/src/engine.rs:1403)). Moreover, the recorder removes tick-0 checkpoints once later checkpoints exist ([lib.rs:788](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-protocol/src/lib.rs:788)), and playback never compares a surviving tick-0 checkpoint ([engine.rs:1420](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-app/src/engine.rs:1420)). A zero-tick replay can therefore report no divergence while returning a different state. ADR-0008 acknowledges the hole, but that does not satisfy the determinism contract.  
   **Fix:** redesign replay time to include canonical screen/UI actions and play through `advance`, or record an authoritative initial snapshot/hash in the header. Compare initial state before tick 0. Version the protocol/ruleset and add a mission replay round-trip beginning before the first dismissal.

3. **High — two high-confidence native semantics are implemented incorrectly.** Native 32 is specified as a barrier after time-taking sequence elements ([scb.md:197](C:/Users/przem/source/repos/opensherwood/docs/formats/scb.md:197)), but it is not collected and simply returns zero ([natives.rs:24](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/natives.rs:24), [natives.rs:200](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/natives.rs:200)). The scheduler consequently launches a walk and immediately processes following elements instead of waiting for arrival ([vm.rs:1491](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:1491)). Native 202 is non-sequence text while 203 blocks for dismissal ([scb.md:243](C:/Users/przem/source/repos/opensherwood/docs/formats/scb.md:243)); although the VM records that distinction, `pending_texts()` discards it and the app turns both into a paused briefing screen ([vm.rs:1204](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:1204), [engine.rs:336](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-app/src/engine.rs:336)).  
   **Fix:** represent native 32 as a real barrier with completion tokens for walks, camera movement and animations. Preserve `TextRequest.blocking` through the app and render 202 as non-modal. Add walk/barrier and 202-versus-203 tests.

4. **High — the VM instruction budget does not bound per-tick work.** Only bytecode dispatch decrements the budget ([vm.rs:1594](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:1594)). Sequence advancement is an unmetered loop while validation permits 4,096 sequences of 4,096 elements each ([vm.rs:933](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:933), [vm.rs:1491](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:1491)). Zone processing can multiply 16,384 classes, 65,536 entities and uncapped polygon lengths ([vm.rs:438](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:438), [vm.rs:1450](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:1450)). One native instruction can also run A* over 4,194,304 cells with infallible allocations and unbudgeted smoothing ([nav.rs:25](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/nav.rs:25), [nav.rs:285](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/nav.rs:285), [nav.rs:404](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/nav.rs:404)). Finally, an accepted `argc` of 16,384 causes `pop_n` to resize despite the stack limit being 4,096 ([vm.rs:505](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:505), [vm.rs:1749](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:1749)).  
   **Fix:** introduce one deterministic work budget covering instructions, native argument work, zone-edge tests, sequence elements, path expansions and line-clear checks. Add aggregate bounds, use fallible allocation, and snapshot/hash incremental work if searches yield across ticks.

5. **High — hostile snapshots can install VM states that are neither fully canonical nor resumable.** `VmState` serializes frames, stacks, budget and counters ([vm.rs:805](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:805)), but budget and counters are absent from both hash encoders and validation ([vm.rs:912](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:912), [vm.rs:1014](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:1014)). Non-empty frames are accepted, then silently discarded by the next callback ([vm.rs:995](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:995), [vm.rs:1578](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:1578)). Counters and `next_text_id` use unchecked `+=`, so a valid hostile snapshot containing `u64::MAX` panics in debug and wraps in release ([vm.rs:1170](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:1170)). This contradicts ADR-0008’s “all runtime state” decision ([ADR-0008:16](C:/Users/przem/source/repos/opensherwood/docs/decisions/ADR-0008-script-vm-ownership.md:16)).  
   **Fix:** either reject every non-quiescent snapshot or implement continuation resumption; remove truly diagnostic fields from authoritative serialization or hash them; use saturating counters/IDs and validate budget/counter invariants.

6. **High — core `Program::validate` does not enforce the translator’s safety assumptions.** It does not require sorted functions, function-local jumps, `LoadParam` bounds, call arity matching the callee, or `Enter` sizes matching metadata ([vm.rs:470](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/vm.rs:470)). The translator checks several of these, but snapshots embed `Program` directly and can recompute its digest, bypassing the translator. RNG validation similarly checks only the numeric stream range, not that gameplay and script streams use the world seed and assigned IDs ([world.rs:953](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/world.rs:953)).  
   **Fix:** make core validation self-sufficient, including aggregate program/argument bounds and expected RNG identities; treat translator checks as earlier diagnostics, not the trust boundary.

7. **High — hostile location values still produce debug/release divergence.** Program locations have no coordinate bound. Native 160 subtracts two `i32` coordinates before converting to `Fixed`, which can overflow ([natives.rs:341](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/natives.rs:341)); camera centering likewise uses unchecked `x - viewport/2` ([world.rs:575](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/world.rs:575)). The public translator also multiplies the tick-rate denominator by 25 without checking ([lib.rs:229](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-script/src/lib.rs:229)).  
   **Fix:** perform coordinate differences in `i64` and clamp explicitly, validate program locations, and use checked rational construction. Add inline-snapshot tests at both `i32` extremes in debug and release.

8. **High — required mission behavior still fails open.** A missing or malformed SCB unconditionally becomes `None` even in strict mode ([mission.rs:204](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-app/src/mission.rs:204)); translation failures also become a mission without a VM, and an unknown map silently receives element-base zero ([mission.rs:467](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-app/src/mission.rs:467)). Mission text/profile-index failures similarly become empty lists and placeholder pages ([engine.rs:276](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-app/src/engine.rs:276)). This allows a retail mission to “load” while its authoritative logic or bindings are absent.  
   **Fix:** fail retail reset on missing/invalid/unbindable SCB and unknown map index spaces by default. Put diagnostic continuation behind an explicit script-leniency option; make text resources required when referenced.

9. **Medium — `ReplayRecorder` still violates its advertised parser-equivalence guarantee.** `finish` neither checks `last.tick <= MAX_TICK` nor reserves capacity before pushing ([lib.rs:792](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-protocol/src/lib.rs:792)); therefore `finish(MAX_TICK + 1)` returns a replay that `from_jsonl` rejects ([lib.rs:496](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-protocol/src/lib.rs:496)). If the last tick equals an existing checkpoint, new final hashes are silently ignored. Separately, headers accept arbitrary viewport, tick-rate and RNG names/algorithms, while playback ignores these fields and resets using only scenario and seed ([lib.rs:362](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-protocol/src/lib.rs:362), [engine.rs:1403](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-app/src/engine.rs:1403)).  
   **Fix:** route final checkpoints through the same validation/allocation path, compare or replace same-tick hashes, and exact-match the header against a freshly constructed session header after reset.

10. **Medium — activation and AI locking have incomplete edge semantics.** Deactivation clears movement but leaves `World.selected` pointing at the inactive actor ([natives.rs:528](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/natives.rs:528)); right-click ordering checks only ID and player kind, so it can queue a path onto that inactive actor ([world.rs:1057](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/world.rs:1057)). `ai_locked` prevents an idle rail program from issuing a new order but does not stop an existing walk or animation ([world.rs:1093](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/world.rs:1093), [world.rs:1120](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/world.rs:1120)); the current test covers only an idle locked guard.  
    **Fix:** clear selection on deactivation and require alive/active at order time. Establish whether “lock/freeze” suspends current actions, document it at the proper confidence, and test locking mid-walk.

11. **Medium — navigation restore can still succeed with a silently unusable grid.** `set_geometry` mutates the world, then calls `ensure_nav`; `ensure_nav` uses `NavGrid::build`, which converts an allocation failure into an empty grid ([world.rs:588](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/world.rs:588), [nav.rs:189](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-core/src/nav.rs:189)). Restore therefore reports success after a failed derived-state allocation. Build-time scan budgets do not address the unbounded A*/smoothing work in finding 4.  
    **Fix:** make `ensure_nav` fallible and construct the grid before committing geometry or restored state; preserve the previous world on every failure.

12. **Medium — RGBA budgeting and renderer totality remain bypassable.** The sprite bank returns a budgeted `Arc<SpriteImage>`, but the renderer adapter clones the entire RGBA vector into a second, unbudgeted, infallibly allocated object on every lookup ([engine.rs:37](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-app/src/engine.rs:37)). Also, `Framebuffer` exposes all fields publicly, while `put` assumes `rgba` matches its declared dimensions; an externally constructed short buffer panics despite the public totality claim ([render/lib.rs:18](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-render/src/lib.rs:18), [render/lib.rs:162](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-render/src/lib.rs:162)).  
    **Fix:** share one frame type/`Arc` across assets and render, or charge every copy with fallible allocation. Make framebuffer invariants private or bounds-check every write.

13. **Medium — the data harness uses a privileged state mutation as player input and misses the decisive cases.** `debug.vm` mutates the VM ([engine.rs:1475](C:/Users/przem/source/repos/opensherwood/crates/opensherwood-app/src/engine.rs:1475)), and `test_script.py` uses it to dismiss every page ([test_script.py:23](C:/Users/przem/source/repos/opensherwood/harness/tests/data/test_script.py:23)), contrary to the rule that `debug.*` is inspection-only and player actions must be canonical ([AGENTS.md:31](C:/Users/przem/source/repos/opensherwood/AGENTS.md:31)). The determinism test compares only final hashes across two same-seed processes; there is no replay, snapshot/restore, per-tick, native-32 walk barrier, native-202, hostile-program or seed-sensitive RNG coverage. The all-script test merely checks `vm.present`, while faults and unknown calls are printed rather than asserted ([test_script.py:73](C:/Users/przem/source/repos/opensherwood/harness/tests/data/test_script.py:73)).  
    **Fix:** first add canonical dismissal, then drive it through `step`; add replay and snapshot continuations, per-tick hashes, seed differentiation, hostile snapshots/programs, and explicit expected trap/stub assertions.

14. **Low — the status report is internally stale and overclaims verification.** It says there are no objectives/dialogues immediately before saying the VM supplies them ([status:14](C:/Users/przem/source/repos/opensherwood/docs/status/2026-09-02.md:14)); reports 25 harness tests although the tree contains 40 `def test_` functions before parametrization ([status:29](C:/Users/przem/source/repos/opensherwood/docs/status/2026-09-02.md:29)); calls navigation bounded despite unbounded search/smoothing; says review-4 findings are “being worked” while its disposition marks them Done ([status:30](C:/Users/przem/source/repos/opensherwood/docs/status/2026-09-02.md:30)); and presents the archery-training loop as working although its triggering hooks are explicitly unwired.  
    **Fix:** distinguish implemented, tested, approximate and known-broken claims; update counts mechanically; link every “verified” behavior to a covering test.
