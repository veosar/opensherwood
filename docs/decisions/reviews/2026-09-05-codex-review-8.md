1. **Critical — the taint model is not dependency-closed and can produce an untainted hypothesis-based win.** `VmState::tainted()` only tests whether a manually populated set is nonempty (`crates/opensherwood-core/src/vm.rs@db32208:1072-1095,1472-1477`). Low-confidence opcode meanings are explicitly implemented without corresponding assumptions (`crates/opensherwood-script/src/lib.rs@db32208:6-9`), as are policy interpretations such as natives 98, 128, 140, and 245 (`natives.rs@db32208:554-557,594-608,624-636,842-849`). Lenient unknown natives return fabricated zero while merely entering `unknown_calls`, without taint (`natives.rs@db32208:348-362`). Most effectful stubs taint only if their result is read; only the curated eight `NEVER_WIN_STUBS` taint on invocation (`natives.rs@db32208:83-87,860-874`). Therefore a script can branch on an uncertain opcode, implemented policy, omitted effect, or lenient result and call `CheckVictoryCondition` while `assumptions` remains empty. Hashing the set makes omissions deterministic, not sound; validation only checks that recorded `StubResult` IDs are stubs (`vm.rs@db32208:1438-1458`).
   **Fix:** redesign around a complete source registry. Conservatively taint a mission when it executes any unverified opcode/native/effect, always taint lenient unknown calls, and whitelist only proven presentation-only stubs. Either propagate provenance through values/effects or statically taint programs containing uncertain operations. Add constructed branch-to-win tests for every source, including snapshot/restore and replay.

2. **High — `CampaignGraph` is written to the world that is immediately discarded.** The debriefing path records the assumption on the completed mission and then calls `reset`, replacing that world (`engine.rs@db32208:1111-1119`). The successor therefore starts with an empty assumption set and can later report an authoritative-looking win even though reaching it depended on the hypothesized graph.
   **Fix:** record `CampaignGraph` on the successfully installed successor world, or carry it through `MissionSpec::assumptions`. Test the successor at tick zero, after snapshot/restore, and through replay. Post-range commit `fe5b030` appears to address this, but it is not in the reviewed endpoint.

3. **High — the `ActionChange` queue retries partially executed handlers, duplicating authoritative effects.** On `CallOutcome::Exhausted`, the queue entry remains (`vm.rs@db32208:1968-2010`), but instructions executed before exhaustion have already mutated class variables, money, entities, or other VM state. `vm_invoke` only tears down frames; it does not roll back mutations (`vm.rs@db32208:2432-2480`). The next tick restarts the handler from its first instruction, so “increment, then exhaust” increments repeatedly. The existing test only exhausts `Hourglass` before the handler starts (`vm.rs@db32208:5049-5110`). Also, a full queue silently drops new changes (`vm.rs@db32208:1950-1964`), which is reachable when an already-backlogged queue receives another tick’s changes.
   **Fix:** execute queued callbacks transactionally and roll back on exhaustion, or persist resumable continuations in snapshot/hash. Treat overflow as a deterministic fault or establish a capacity that cannot overflow. Add increment-then-spin, native-side-effect-then-spin, restore-mid-backlog, and full-queue tests.

4. **High — `AI_WORK_PER_TICK` still does not bound all AI work.** Perception is now charged and cursor-backed, but `advance_state` scans every entity without charge, while `attack_orders` performs an uncharged linear target lookup per attacker (`ai.rs@db32208:500-510,716-740`), allowing quadratic work in an accepted hostile snapshot. More importantly, patrol/program path requests run after `ai_tick` and each obtains a fresh `ORDER_SEARCH_WORK` budget (`world.rs@db32208:1578-1627,835-840`). Thus thousands of idle guards can still initiate thousands of independent searches per tick, contrary to the review-7 claim that one budget pays for everything.
   **Fix:** use one authoritative simulation AI/navigation budget across perception, transitions, target resolution, attacks, and patrol/program planning. Pre-index entity IDs and persist phase-specific cursors so exhaustion resumes fairly. Add maximum attack-target and mass idle-patrol tests; the current test covers only mass alert searches (`ai.rs@db32208:1496-1575`).

5. **High — campaign money is only mission-local, and replay initialization omits it.** The mission is seeded from `ProfileSummary.money` (`engine.rs@db32208:1783-1787`), but there is no code that writes the live VM money back to the selected profile. Script changes therefore disappear on the next mission or process restart. Persisted `u32` money above `i32::MAX` silently becomes zero through `try_from(...).unwrap_or(0)`. Although live VM money is hashed and snapshotted, `ResetParams` and `ReplayHeader` contain no starting money (`opensherwood-protocol/src/lib.rs@db32208:136-144,335-358`). Playback resets using the current profile, so changing `profiles.json` makes an otherwise valid replay unreproducible until the tick-zero hash rejects it. ADR-0004 also incorrectly says mission specs themselves were added to snapshot schema 13 (`docs/decisions/ADR-0004-protocol.md@db32208:36-40`).
   **Fix:** define a single signed money type and campaign transition policy, copy live money into the profile at authoritative transitions, and persist it atomically. Put canonical starting money in the replay header and use that recorded value during playback. Add spend/earn → win → successor → restart and replay-after-profile-change tests.

6. **High — native-result validation is lexical, not control-flow sound.** `Program::validate` accepts `GetNativeResult` when the preceding array element is a result-producing `Native` (`vm.rs@db32208:601-625`), but jumps may target that result-read instruction directly (`vm.rs@db32208:647-648`). A hostile validated program can skip the native and consume the frame’s initialized `native_result=0`, `last_native=0` (`vm.rs@db32208:2667-2678`), without stub taint. The table’s `has_result` field is also described partly as corpus usage rather than an established semantic return contract (`natives.rs@db32208:89-103`).
   **Fix:** fuse native call/result into one IR instruction, or run control-flow dataflow proving every predecessor executed the same result-producing native and forbid jumps into result readers. Separate `returns_value` from “retail corpus observed a read.” Add direct-jump, divergent-predecessor, and loop-entry validation tests.

7. **High — profile/settings persistence can silently lose or accept invalid data.** `save_profiles` and `apply_settings` directly overwrite files and do not create the artifact parent (`engine.rs@db32208:717-748,766-793`); a fresh default `harness/out` therefore makes the first write fail after the UI already reports success (`main.rs@db32208:51-56`). Reads are unbounded and accept unlimited profiles and unchecked difficulty, percentages, money, aspect, volume, and enum-like indices. The selected index uses truncating `u64 as usize`. Writes are non-atomic, so interruption can truncate the only copy. Existing tests inspect a file within the creating process but never start a second session or exercise malformed input (`harness/tests/data/test_menu.py@db32208:165-193,204-231`).
   **Fix:** use versioned persistence documents with size/range/count validation, checked conversions, parent creation, and temp-file-plus-rename writes. Surface persistence failure to the UI. Add fresh-directory, reload, truncation, oversized, invalid-range, duplicate-name, and corrupted-JSON tests.
